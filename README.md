# MongoDB — домашняя работа (вариант на Python)

Решение написано на Python 3.13 с официальным драйвером **PyMongo 4.18**, асинхронный API
(`AsyncMongoClient`). Данные, контракты и сценарии комплекта сохранены.

## Запуск

Сеть стенда объявлена `internal`, порты узлов наружу не опубликованы, поэтому приложение
запускается так же, как `lab` из комплекта, — сервисом в сети Compose, с тем же URI:

```
mongodb://m1:27017,m2:27017,m3:27017/hw2?replicaSet=hw2rs&retryWrites=true&serverSelectionTimeoutMS=10000&readPreference=primary
```

```
docker compose up -d                      # три узла и replica set
docker compose run --rm py help           # список команд
docker compose run --rm py reset          # 6 товаров и 35 заказов; прежние результаты сбрасываются
docker compose run --rm py fixtures       # контрольные данные и эталоны
docker compose run --rm py data           # разделы 2–3: валидатор, поиск, история, отчёт
docker compose run --rm py index          # раздел 4: explain до и после индекса, 10 000 заказов
docker compose run --rm py purchase       # раздел 5: покупка, откат, повтор, конфликт, счётчики
docker compose run --rm py failover       # раздел 6: смена primary тем же клиентом
docker compose run --rm py all            # четыре сценария подряд
docker compose down                       # остановить стенд
```

Образ собирается при первом запуске; после изменения зависимостей — `docker compose build py`.
Код монтируется в контейнер, пересборка после правок не нужна. Результаты в
`results/results.json` получены командами `py reset` и `py all` (подробнее — раздел 8).

| Файл | Назначение |
|---|---|
| `compose.yaml`, `lab.js`, `solution.js` | Комплект, без изменений |
| `compose.override.yaml`, `Dockerfile` | Сервис `py` в той же сети; Compose подхватывает override сам |
| `lab.py` | Порт `lab.js`: те же данные, сценарии и проверки в том же порядке, тот же `results/results.json` |
| `solution.py` | Решение |
| `results/results.json` | Фактические результаты всех сценариев |

Что сохранено из комплекта:

- **Данные.** `py reset` и `lab reset` дают одинаковый `dbHash` коллекций `products` и `orders`
  (в обоих режимах, 35 и 10 000 заказов), то есть документы совпадают побайтно, включая
  BSON-типы.
- **Контракты.** Вход операции — словарь с ключами контракта, выход — список полных документов:
  `await search_products(db, {"category": "clothes", "size": "L", "qty": 2})`,
  `await history(db, {"userId": 2500, "status": "paid"})`, `await report(db, start, end)`.
  Покупка — `await purchase(db, request, trace)`: возвращает полный заказ, отказ — исключение
  `HWError` с полем `code` (`ITEM_UNAVAILABLE` или `REQUEST_CONFLICT`). Опыт со сменой primary —
  `await write_probe(db, id, message)` и `await read_probe(db, id)`.
- **Сценарии.** Проверки и их названия перенесены из `lab.js`; результаты пишутся в
  `results/results.json` в том же формате (canonical Extended JSON), `solutionHash` считается
  по `solution.py`. Сверх `lab.js` сохраняются время выполнения в сводке планов (раздел 4) и
  журнал событий драйвера при смене primary (раздел 6).

## Раздел 2. Данные и запросы

### Валидатор `products`

`install_validator` ставит `$jsonSchema` через `collMod` с `validationLevel: strict` и
`validationAction: error` (схема — `PRODUCTS_VALIDATOR` в `solution.py`). `strict` означает, что
правила применяются ко всем вставкам и обновлениям, `error` — что нарушающая запись отклоняется,
а не попадает в лог.

База проверяет то, что можно сказать об одном документе:

- обязательные поля `_id`, `name`, `category`, `price`, `variants`;
- типы: строки, `price` — `decimal`, `variants` — массив объектов;
- структуру элемента `variants`: обязательные `size` (строка) и `stock` (`int` или `long`);
- неотрицательность `price` и `stock` (`minimum: 0`).

`additionalProperties` не задан: служебные поля заданием разрешены.

Результат сценария `data` (`artifacts.data.validation` в `results/results.json`):

| Документ | Результат | `errInfo` |
|---|---|---|
| `valid` | принят | — |
| `string-price` (`price: "100.00"`) | код 121 | `price` → `bsonType`: ожидался `decimal`, `consideredType: "string"` |
| `negative-stock` (`stock: -1`) | код 121 | `variants` → `items[0]` → `stock` → `minimum: 0`, `consideredValue: -1` |

Причина отказа — именно валидатор: код 121 — `DocumentValidationFailure`, а в
`errInfo.details.operatorName` стоит `$jsonSchema` с указанием нарушенного правила.

Что остаётся приложению:

- **Уникальность размеров внутри товара.** `uniqueItems` сравнивает элементы целиком, поэтому
  `{size: "L", stock: 0}` и `{size: "L", stock: 5}` для него различны. Инвариант держит код,
  который меняет каталог.
- **Ссылки.** Что `items[].sku` указывает на существующий товар, а `items[].size` — на его
  вариант, база не проверяет: внешних ключей нет.
- **Правила, зависящие от операции**, — например, хватает ли остатка для покупки. Валидатор
  здесь последний рубеж: остаток не может стать отрицательным ни при каком обновлении.

### Поиск товаров

```python
db.products.find({
    "category": category,
    "variants": {"$elemMatch": {"size": size, "stock": {"$gte": qty}}},
}).sort("_id", ASCENDING)
```

`$elemMatch` требует, чтобы оба условия выполнил **один** элемент массива. Запрос через
точечную нотацию `{"variants.size": "L", "variants.stock": {"$gte": 2}}` этого не требует:
каждое условие может выполнить свой элемент. На контрольных данных у товара A размер L имеет
остаток 0, а M — 10:

| Запрос `clothes`, L, 2 | Результат |
|---|---|
| точечная нотация | `A, B, C` — A попал ошибочно: размер L есть, остаток ≥ 2 есть у M |
| `$elemMatch` | `B, C` |
| `$elemMatch` после изменения A/L на 2 | `A, B, C` |

Возвращается документ целиком, со всеми вариантами, а не только с совпавшим: проекции нет.
Порядок — `_id` по возрастанию. Коллекции созданы без собственной collation, поэтому строки
сравниваются побайтно (simple collation), с учётом регистра.

Другие значения параметров на общем наборе:

| Вход | Результат | Что меняется |
|---|---|---|
| `clothes`, L, 2 | `B, C` | — |
| `clothes`, M, 5 | `A` | размер и количество |
| `accessories`, L, 3 | `D` | категория |
| `clothes`, L, 99 | `[]` | нет совпадений |

### История заказов

```python
db.orders.find({"userId": user_id, "status": status})
    .sort([("createdAt", DESCENDING), ("_id", ASCENDING)])
    .limit(20)
```

Второй ключ сортировки обязателен: у заказов с равным `createdAt` порядок без него не определён,
и граница в 20 документов могла бы резать пару по-разному от запуска к запуску. `_id` уникален,
поэтому порядок полный.

| Проверка | Результат |
|---|---|
| `{userId: 2500, status: "paid"}` | 20 заказов из 31 подходящего: `H24, H25, H22, H23, …, H06, H07` |
| равные даты | в каждой паре с одним `createdAt` сначала меньший `_id` (`H24` перед `H25`) |
| состав | полные документы, совпадают с контрольными по всем полям |
| другой покупатель `{2501, "paid"}` | `other-user` |
| другой статус `{2500, "cancelled"}` | `other-status, excluded-cancelled` |
| нет совпадений `{9999, "paid"}` | `[]` |

### Модель данных

**Почему позиции встроены в заказ.** Позиция не существует отдельно от заказа: она создаётся
вместе с ним, читается вместе с ним (история возвращает заказ целиком) и после покупки не
меняется. Число позиций ограничено размером корзины, до предела документа в 16 МБ далеко.
Встраивание даёт чтение заказа одним обращением и атомарную запись: заказ со всеми позициями
появляется одной вставкой одного документа, состояния «заказ есть, а позиций ещё нет» не бывает.

**Почему история покупателя — отдельные документы.** Заказов у покупателя неограниченно много,
и список только растёт. Массив заказов внутри документа покупателя рос бы без предела: каждое
добавление переписывало бы всё более крупный документ, все покупки одного покупателя
конкурировали бы за него, а в конце ждал бы предел в 16 МБ. Кроме того, у заказа своя жизнь:
собственный идентификатор (`_id` равен `operationId` покупки) и статус, который меняется
независимо от остальных заказов. И запросы к истории — это запросы к множеству: фильтр по
статусу, сортировка, первые 20. Коллекция с индексом отвечает на них, читая только нужные
документы; из массива пришлось бы доставать весь документ. Связь хранится на стороне «много»:
заказ ссылается на покупателя полем `userId`.

**Какой факт представляет цена в позиции заказа.** Цену единицы товара в момент покупки —
условие состоявшейся сделки. `products.price` отвечает на вопрос «сколько товар стоит сейчас» и
меняется; `items[].price` отвечает на вопрос «по какой цене его купили» и не меняется никогда.
Поэтому это копия, а не ссылка на каталог: если бы заказ хранил только `sku`, изменение цены в
каталоге задним числом переписало бы суммы всех прошлых заказов. В контрольных данных это видно
на заказе `sale-middle`: товар A куплен по 120.00, хотя в каталоге стоит 100.00.

## Раздел 3. Отчёт о продажах

### Pipeline

`report(db, start, end)` в `solution.py`; весь расчёт выполняет MongoDB, Python получает пять
готовых строк:

```python
db.orders.aggregate([
    {"$match": {"status": "paid", "createdAt": {"$gte": start, "$lt": end}}},
    {"$unwind": "$items"},
    {"$group": {
        "_id": "$items.sku",
        "qty": {"$sum": "$items.qty"},
        "revenue": {"$sum": {"$multiply": ["$items.qty", "$items.price"]}},
    }},
    {"$sort": {"revenue": -1, "_id": 1}},
    {"$limit": 5},
    {"$lookup": {"from": "products", "localField": "_id", "foreignField": "_id", "as": "product"}},
    {"$unwind": "$product"},
    {"$project": {"_id": 0, "sku": "$_id", "name": "$product.name", "qty": "$qty", "revenue": "$revenue"}},
])
```

1. **`$match`** — только оплаченные заказы периода: `$gte` включает начало, `$lt` исключает конец.
   Стоит первым, чтобы дальше шло как можно меньше документов (и чтобы при наличии индекса
   отбор шёл по нему).
2. **`$unwind: "$items"`** — от заказов к позициям: один документ на позицию.
3. **`$group` по `items.sku`** — объединяет все размеры и все заказы одного товара: `qty` — сумма
   количеств, `revenue` — сумма `qty × items.price`. Цена берётся из позиции заказа, а не из
   каталога. `$multiply` целого на Decimal128 и `$sum` decimal-значений дают Decimal128: деньги
   считаются в десятичной арифметике, без ошибок двоичной плавающей точки.
4. **`$sort {revenue: -1, _id: 1}`** — по выручке, при равной выручке — по артикулу. У A и B
   поровну 320.00; без второго ключа их порядок не был бы определён.
5. **`$limit: 5`** — топ-5. Вместе с `$sort` сервер выполняет его как top-k сортировку: в памяти
   держатся только пять лучших строк.
6. **`$lookup`** — название из `products` по `_id` (через индекс `_id`). Стоит после `$limit`,
   поэтому соединение выполняется для пяти строк, а не для каждого проданного товара. Эта и
   следующие стадии порядок строк не меняют.
7. **`$unwind: "$product"`** — массив из одного найденного товара превращается в объект. Товары
   из каталога не удаляются, поэтому строка не теряется.
8. **`$project`** — форма контракта `{sku, name, qty, revenue}`.

### Сверка с эталоном

Результат сценария `data` (`artifacts.data.report`), период `[2026-01-01, 2026-02-01)`:

| # | sku | name | qty | revenue |
|---|---|---|---:|---:|
| 1 | A | Футболка | 3 | 320.00 |
| 2 | B | Рубашка | 4 | 320.00 |
| 3 | C | Толстовка | 3 | 270.00 |
| 4 | D | Ремень | 2 | 240.00 |
| 5 | E | Сумка | 1 | 200.00 |

Совпадает с эталоном построчно, включая порядок (проверка `report top 5 amounts/order/names`).
Шестой проданный товар — F (`sale-last`, 1 × 150.00) — отсечён `$limit`. `revenue` сохранён как
Decimal128 (`{"$numberDecimal": "320.00"}` в `results.json`).

| Проверка | Данные | Результат |
|---|---|---|
| начало включается | `sale-start` создан ровно в `2026-01-01T00:00:00Z`; отчёт за `[from, from + 1 мс)` | B 320.00, A 200.00 — только этот заказ (`from included`) |
| конец исключается | `excluded-end` создан ровно в `2026-02-01T00:00:00Z`, A × 999 | не учтён, иначе у A было бы 1002 шт. |
| раньше начала | `excluded-before` — `2025-12-31T23:59:59.999Z`, A × 999 | не учтён |
| последняя миллисекунда периода | `sale-last` — `2026-01-31T23:59:59.999Z` | учтён: D, E, F |
| неоплаченные | `excluded-created`, `excluded-cancelled` внутри периода, A × 999 | не учтены: `status: "paid"` в `$match` |
| пустой период | `[2024-01-01, 2024-02-01)` | `[]` (`empty interval`) |

### Изменение цены в каталоге

После отчёта сценарий меняет цену A в каталоге на 999.00 и повторяет отчёт (`afterPriceReport`):
строки те же, у A по-прежнему 3 шт. и 320.00 (проверка `catalog price does not rewrite revenue`).
Выручка считается по `items.price` — цене, зафиксированной в заказе при покупке; из каталога
`$lookup` берёт только название.

### Расчёт одного товара: A (Футболка)

| Заказ | createdAt | status | Позиция | qty | price | qty × price | В отчёте |
|---|---|---|---|---:|---:|---:|---|
| `sale-start` | 2026-01-01T00:00:00Z | paid | A / M | 2 | 100.00 | 200.00 | да — ровно начало периода |
| `sale-middle` | 2026-01-15T12:00:00Z | paid | A / L | 1 | 120.00 | 120.00 | да |
| `excluded-end` | 2026-02-01T00:00:00Z | paid | A / M | 999 | 100.00 | — | нет — конец периода исключён |
| `excluded-before` | 2025-12-31T23:59:59.999Z | paid | A / M | 999 | 100.00 | — | нет — раньше начала |
| `excluded-created` | 2026-01-15T00:00:00Z | created | A / M | 999 | 100.00 | — | нет — не оплачен |
| `excluded-cancelled` | 2026-01-15T00:00:00Z | cancelled | A / M | 999 | 100.00 | — | нет — отменён |
| **Итого** | | | | **3** | | **320.00** | `{sku: "A", qty: 3, revenue: 320.00}` |

Размеры M и L сложены в одну строку. Позиция `sale-middle` куплена по 120.00 при каталожной цене
100.00: по каталогу вышло бы 300.00, по ценам покупки — 320.00.

## Раздел 4. Индекс и план выполнения

### Опыт

Сценарий `index`: набор из 10 000 заказов (`G00000`…`G09999`), в начале только индекс `_id_`.
Запрос истории `{userId: 2500, status: "paid"}`, сортировка `{createdAt: -1, _id: 1}`,
`limit 20`; под фильтр подходят 1600 заказов. Планы сняты до создания индекса и после, на
неизменном наборе; полные планы — `artifacts["explain-before"]` и `artifacts["explain-after"]`,
сводка и обе выдачи — `artifacts.index`.

Результат и план получают один и тот же запрос — курсор `history_cursor`. `AsyncCursor.explain()`
в PyMongo всегда запрашивает verbosity `allPlansExecution`, поэтому `lab.py` строит команду
`explain` из того же курсора (фильтр, сортировка, limit) с `verbosity: "executionStats"` —
это аналог `cursor.explain("executionStats")` в mongosh. Отправленная команда сохранена в плане
(поле `command`).

```python
HISTORY_INDEX = {"userId": 1, "status": 1, "createdAt": -1, "_id": 1}
db.orders.create_index(HISTORY_INDEX, name="history_user_status_date_id")
```

### Сравнение

| Вариант | nReturned | totalKeysExamined | totalDocsExamined | Есть отдельная SORT |
|---|---:|---:|---:|---|
| До индекса | 20 | 0 | 10000 | да |
| После индекса | 20 | 20 | 20 | нет |

`executionTimeMillis`: 2 мс до и 0 мс после. На 10 000 небольших документов время в пределах
шума, поэтому сравнение строится на объёме работы, а не на времени.

Выдача не изменилась: 20 `_id` и их порядок до и после совпадают (`same IDs and order`) и
совпадают с независимым расчётом в Python по исходным данным (`matches independent fixture
order`): `G09928, G09929, G09924, G09925, …` — пары с одинаковым `createdAt` идут по
возрастанию `_id`.

### Планы

До индекса:

```
SORT {createdAt: -1, _id: 1}, limitAmount 20       nReturned 20
└─ COLLSCAN, filter {status: "paid", userId: 2500}  docsExamined 10000, nReturned 1600
```

После индекса:

```
LIMIT 20                                           nReturned 20
└─ FETCH                                           docsExamined 20
   └─ IXSCAN history_user_status_date_id           keysExamined 20
      indexBounds: userId [2500, 2500], status ["paid", "paid"],
                   createdAt [MaxKey, MinKey], _id [MinKey, MaxKey]
```

`rejectedPlans` пуст в обоих планах: других кандидатов у планировщика не было.

### Объяснение

**Как работал запрос до индекса.** COLLSCAN читает все 10 000 документов и проверяет фильтр
у каждого; 1600 подошедших уходят в SORT. SORT — блокирующая стадия: прежде чем отдать первую
строку, она должна получить все 1600 (с limit это top-k сортировка — в памяти 20 лучших, но
просмотреть нужно всё).

**Как работает после.** Границы индекса выделяют один непрерывный участок ключей
`userId = 2500, status = "paid"`, и внутри него ключи уже лежат по `createdAt` по убыванию, а при
равной дате — по `_id` по возрастанию, то есть ровно в порядке сортировки запроса. Поэтому
отдельной SORT нет, а LIMIT останавливает сканирование на 20-м ключе: 20 ключей и 20 документов
вместо 10 000 документов.

**Порядок полей — правило ESR.**

- **Equality — `userId`, `status`.** Поля с условием равенства идут первыми: после фиксации их
  значений остаётся один непрерывный участок индекса, внутри которого следующие поля
  упорядочены. Между собой их порядок для этого запроса не важен; `userId` стоит первым, потому
  что история — всегда запрос одного покупателя, и префикс `{userId}` подходит также для истории
  без фильтра по статусу.
- **Sort — `createdAt: -1`, `_id: 1`.** Поля сортировки идут сразу за полями равенства, в том же
  порядке и с теми же направлениями, что в `sort`. Подошёл бы и полностью обратный индекс
  `{createdAt: 1, _id: -1}` (его читают в обратную сторону), а `{createdAt: -1, _id: -1}` — нет.
  `_id` нужен в индексе: без него ключи упорядочены только по дате, порядок заказов с равным
  `createdAt` (в наборе они идут парами) не определён, и планировщик добавил бы SORT.
- **Range** — диапазонных условий в запросе нет.

Если бы поле сортировки стояло раньше поля равенства (`{createdAt: -1, userId: 1, …}`), индекс
пришлось бы сканировать по всем покупателям, отбрасывая чужие ключи.

**Издержка индекса.** Каждая вставка и удаление заказа, а также изменение `userId`, `status`
или `createdAt` теперь обновляют ещё и B-дерево этого индекса: покупка, вставляющая заказ,
делает дополнительную запись в индекс. Индекс занимает место на диске и в кеше WiredTiger, а
его построение на большой коллекции — отдельная нагрузка. Для частого запроса истории это
оправдано, а лишние индексы замедляли бы запись без выигрыша при чтении.

**hint** не применялся (`USES_HISTORY_HINT = False`, в результатах `hint: false`): планировщик
выбрал индекс сам.

## Раздел 5. Оформление заказа

### Оболочка транзакции: начало, commit и abort

`transaction(db, body)` в `solution.py` — перенос оболочки `transaction()` из `lab.js`:

```python
async with db.client.start_session(causal_consistency=True) as session:       # 1
    await session.start_transaction(                                           # 2
        read_concern=ReadConcern("snapshot"),
        write_concern=WC,                    # {w: "majority", j: true, wtimeout: 10000}
        read_preference=ReadPreference.PRIMARY,
    )
    try:
        result = await body(session)                                           # 3
    except BaseException:
        await session.abort_transaction()                                      # 4
        raise
    await session.commit_transaction()                                         # 5
    return result
```

1. Одна явная сессия на покупку. Каждая операция покупки получает `session=session`: только
   тогда драйвер добавляет к команде `lsid`, `txnNumber` и `autocommit: false`, и она входит в
   транзакцию. Операция без `session` выполнилась бы отдельно и не откатилась бы.
2. `start_transaction` ничего не отправляет на сервер — запоминает настройки. Транзакция
   начинается с первой операцией (`startTransaction: true`), на ней же растёт `totalStarted`.
3. `body` — сама покупка.
4. Любое исключение из `body` — бизнес-отказ `HWError` или ошибка базы — ведёт к
   `abortTransaction`: сервер отбрасывает все изменения транзакции. Исключение пробрасывается
   дальше, поэтому код ошибки попадает в результат опыта.
5. `body` завершился без исключения — `commitTransaction`: изменения всех документов становятся
   видимы разом. Ошибку commit оболочка не выдаёт за abort: при обрыве связи исход commit может
   быть неизвестен.

При выходе из `async with` сессия закрывается; если транзакция всё ещё открыта (например,
commit не дошёл до сервера), `end_session` её прерывает.

`session.with_transaction()` не используется сознательно: он сам повторяет всю транзакцию при
`TransientTransactionError` и commit при `UnknownTransactionCommitResult`. Опыты задания — без
повторных попыток, и с этой оболочкой каждая покупка — ровно одна серверная транзакция.

### Покупка внутри транзакции

`purchase(db, request, trace)`, сокращённо (все операции — с `session=session`):

```python
saved = await db.orders.find_one({"_id": operation_id})                 # 1. повтор?
if saved:
    return saved, если userId и позиции совпадают, иначе HWError("REQUEST_CONFLICT")
for item in request["items"]:                                           # 2. списания по порядку
    result = await db.products.update_one(
        {"_id": sku, "variants": {"$elemMatch": {"size": size, "stock": {"$gte": qty}}}},
        {"$inc": {"variants.$.stock": -qty}})
    trace({"event": "update_inside_transaction", "sku": sku,
           "matched": result.matched_count, "modified": result.modified_count})
    if result.modified_count != 1:
        raise HWError("ITEM_UNAVAILABLE")
    price = (await db.products.find_one({"_id": sku}, {"price": 1}))["price"]
await db.orders.insert_one({"_id": operation_id, "userId": user_id, "createdAt": now,   # 3. заказ
                            "status": "created", "items": [{sku, size, qty, price}, ...]})
```

- **Проверка остатка — в условии обновления.** `$elemMatch` требует, чтобы размер и
  `stock >= qty` относились к одному варианту, а `$inc` по позиционному `variants.$` списывает
  именно его. Проверка и списание — одна атомарная операция над документом: между ними никто
  не вклинится. Нет товара, размера или остатка — фильтр ничего не находит, `matched: 0,
  modified: 0`, и покупка отказывает с `ITEM_UNAVAILABLE`. Валидатор `products` (`stock >= 0`)
  остаётся последним рубежом.
- **Без предварительных проверок.** Покупка не читает остатки заранее: первое списание реально
  выполняется, а отказ второго откатывает его.
- **Цена, дата и статус** определяются здесь: цена читается из каталога в той же транзакции и
  копируется в позицию, `createdAt` — текущее время UTC, усечённое до миллисекунд (точность BSON
  Date), чтобы возвращённый заказ совпадал с сохранённым; `status` — `"created"`. Позиции идут в
  порядке запроса.

### Как код приходит к commit или abort

| Случай | Путь в коде | Конец транзакции | Результат |
|---|---|---|---|
| Новая успешная покупка | заказа нет → два списания с `modified: 1` → вставка заказа | commit | новый `Order` |
| Повтор с теми же параметрами | заказ найден, параметры совпали → возврат без записей | commit транзакции, которая только читала | сохранённый `Order` |
| Тот же `operationId`, другие параметры | заказ найден, параметры отличаются → `HWError` | abort | `REQUEST_CONFLICT` |
| Нет товара, размера или остатка | списание с `modified: 0` → `HWError`, в том числе после успешного первого | abort, первое списание отменяется | `ITEM_UNAVAILABLE` |
| Ошибка базы внутри покупки | исключение драйвера | abort | исключение пробрасывается |

### Настройки транзакции

| Настройка | Значение | Зачем |
|---|---|---|
| `readConcern` | `snapshot` | все чтения транзакции (заказ, цены) видят один согласованный снимок данных плюс собственные записи |
| `writeConcern` | `{w: "majority", j: true, wtimeout: 10000}` | commit подтверждается, когда транзакция записана в журнал на большинстве узлов: подтверждённая покупка переживёт смену primary; `wtimeout` ограничивает ожидание подтверждения |
| `readPreference` | `primary` | транзакция выполняется на primary: все её операции идут на один узел |
| сессия | `causal_consistency=True` | как в оболочке комплекта; для одной транзакции роли не играет |

### Опыты

Сценарий `purchase`; исходные остатки: A — L 0 / M 10, B — L 5 / M 4.

**Откат после первого списания** — `rollback-001`: A/M × 2, B/L × 6 (у B/L только 5):

```
TX {"event": "update_inside_transaction", "sku": "A", "matched": 1, "modified": 1}   A/M 10 → 8 внутри транзакции
TX {"event": "update_inside_transaction", "sku": "B", "matched": 0, "modified": 0}   B/L: 5 < 6, условие не выполнено
→ HWError("ITEM_UNAVAILABLE") → abortTransaction
```

После abort: A/M = 10, B/L = 5, заказов нет — документы `products` и `orders` целиком совпадают
с исходными (`abort restores both full documents and leaves no order`), операция вернула
`ITEM_UNAVAILABLE`. Первое списание было настоящим (`modified: 1`), но существовало только
внутри транзакции и отброшено при abort; компенсирующих записей нет.

**Успешная покупка** — `purchase-001`: A/M × 2, B/L × 1:

| | A (L / M) | B (L / M) | Заказы |
|---|---|---|---|
| до | 0 / 10 | 5 / 4 | — |
| после | 0 / **8** | **4** / 4 | `purchase-001` |

Остальные товары и варианты не изменились (`success changes only selected stocks`). Возвращённый
документ совпадает с сохранённым (`returned order is saved order`):

```json
{"_id": "purchase-001", "userId": 2500, "createdAt": {"$date": "2026-10-21T11:36:45.146Z"}, "status": "created",
 "items": [{"sku": "A", "size": "M", "qty": 2, "price": {"$numberDecimal": "100.00"}},
           {"sku": "B", "size": "L", "qty": 1, "price": {"$numberDecimal": "80.00"}}]}
```

BSON-типы в базе: `userId` и `qty` — int, `price` — decimal, `createdAt` — date.

**Повтор** — тот же `purchase-001` после того, как цена A в каталоге стала 777.00, а ключи
запроса переставлены (`{userId, items: [{qty, size, sku}], operationId}`): вернулся тот же заказ
с той же датой и ценами 100.00 / 80.00; остатки и заказы не изменились (`replay no writes
despite changed catalog price/key order`).

**Конфликт** — `purchase-001` с `qty: 3` в первой позиции, без сброса данных после повтора:
`REQUEST_CONFLICT`, данные не изменены.

**Нет размера и нет SKU** — `missing-001` (B/XXL) и `unknown-001` (`NO_SUCH_SKU`), в обоих
случаях после успешного списания A: `ITEM_UNAVAILABLE`, состояние откатилось к прежнему.

### Атомарность и защита от повторного запроса

**Атомарность** — свойство одной транзакции: два списания и заказ применяются вместе или не
применяются вовсе. Она отвечает на вопрос «что будет, если покупка оборвётся на середине» —
откат, как в опыте выше.

О бизнес-запросах атомарность ничего не знает. Клиент отправил покупку, транзакция
закоммитилась, а ответ потерялся (таймаут, обрыв связи). Клиент повторяет запрос — и без
дополнительной защиты выполнится вторая, тоже атомарная транзакция: остатки спишутся дважды,
заказов станет два. Две корректные транзакции дают неверный бизнес-результат.

**Защита от повтора** — `operationId`, который клиент создаёт один раз на покупку и повторяет
при повторных попытках:

- `orders._id = operationId`: уникальный индекс `_id` не даст появиться второму заказу с тем же
  `operationId`;
- в начале транзакции покупка ищет заказ с этим `_id`; если он найден и параметры совпали,
  возвращается сохранённый заказ без новых записей;
- если параметры отличаются — `REQUEST_CONFLICT`: тот же идентификатор пришёл с другой покупкой,
  и молча вернуть чужой заказ или создать новый было бы ошибкой;
- сравниваются значения `userId` и `(sku, size, qty)` по позициям в порядке запроса, а не текст
  JSON: порядок ключей и int32/int64 не важны, текущая цена каталога не участвует;
- если два одинаковых запроса выполняются одновременно, вставить заказ с одним `_id` сможет
  только один; второй получит конфликт записи или дубликат ключа, его транзакция прервётся, а
  списания откатятся. Повтор этого запроса вернёт сохранённый заказ. Конкурентный тест заданием
  не требуется.

Это защита другого уровня, чем `retryWrites=true`: retryable writes не дают драйверу дважды
применить одну команду, которую он сам повторил (сервер узнаёт её по `lsid` + `txnNumber`).
Повтор бизнес-запроса — новый вызов, новая сессия и новая транзакция; распознать его может
только приложение, по `operationId`.

### Счётчики транзакций

Снимки `serverStatus().transactions` — `artifacts["transactions-rollback"]` и
`artifacts["transactions-success"]`: полный раздел `transactions` до и после, `host`, `pid`,
`uptime`, `localTime` и разности. Все снимки сняты с одного primary (`host: a1ddbdc0f4dd` — имя
контейнера `m2`) и одного процесса (`pid: 1`, `uptime: 432` с), `sameProcess: true`.

| Опыт без повторных попыток | Δ totalStarted | Δ totalCommitted | Δ totalAborted |
|---|---:|---:|---:|
| Новая успешная покупка | 1 | 1 | 0 |
| Откат после первого списания | 1 | 0 | 1 |

Абсолютные значения `totalStarted / totalCommitted / totalAborted`: откат — 0/0/0 → 1/0/1,
успех — 1/0/1 → 2/1/1. Каждая покупка — ровно одна серверная транзакция: оболочка повторов не
делает, а commit и abort драйвер повторил бы только после сетевой ошибки или смены primary,
которых не было. Счётчики подтверждают, что сервер видел транзакцию и её исход; сам откат
доказывают состояния данных до и после.

## Раздел 6. Смена primary

### Опыт

Сценарий `failover`, база `hw2_failover`. Все операции выполняет один экземпляр
`AsyncMongoClient`, созданный по URI со списком всех узлов и `replicaSet=hw2rs`; адрес вручную не
меняется. Результат — `artifacts.failover`.

| Шаг | Результат |
|---|---|
| Роли до (`replSetGetStatus`) | m1 SECONDARY, **m2 PRIMARY**, m3 SECONDARY; драйвер видит то же: m2 — RSPrimary |
| Запись `before` с `{w: "majority", j: true, wtimeout: 10000}` | `acknowledged: true`, `electionId …0007`, `opTime.t: 7` |
| `replSetStepDown: 60, secondaryCatchUpPeriodSecs: 10` | `ok: 1` |
| Роли после | **m1 PRIMARY**, m2 SECONDARY, m3 SECONDARY; драйвер: m1 — RSPrimary |
| Чтение `before` тем же клиентом | `{"_id": "before", "message": "majority confirmed before stepDown"}` |
| Запись `after` тем же клиентом и с тем же write concern | `acknowledged: true`, `electionId …0008`, `opTime.t: 8` |
| Повторы в сценарии | 0 |
| Документы в `probe` | `after`, `before` |

`electionId` и срок (term) в `opTime` выросли на единицу: запись после переключения подтвердил
другой primary, избранный на следующем сроке.

Журнал драйвера (`driverEvents`, время от отправки stepDown):

| Время | Узел | Что узнал драйвер |
|---|---|---|
| +1 мс | m2 | ответ на ожидающий hello: RSOther — узел слагает полномочия и уже не primary |
| +18 мс | m2 | RSSecondary |
| +26 мс | m1 | ответ на ожидающий hello: RSPrimary |
| +33 мс | — | чтение и новая запись выполнены |

Отказов команд нет: ни одна операция не попала на бывший primary, так что повторять было нечего.

### Как клиент находит новый primary

1. **Seed list и имя набора.** URI перечисляет `m1`, `m2`, `m3` и `replicaSet=hw2rs`. Драйвер
   подключается к узлам, из ответов `hello` узнаёт состав набора и роли (`setName`,
   `isWritablePrimary`, `secondary`, `hosts`) и строит описание топологии. Заранее знать, кто
   primary, не нужно.
2. **Мониторинг (SDAM).** К каждому узлу у драйвера отдельное служебное соединение. С MongoDB
   4.4 оно работает в потоковом режиме: драйвер отправляет «ожидающий» hello, и сервер отвечает
   не по таймеру, а сразу при изменении своего состояния. Отсюда `awaited: true` в журнале: m2
   сообщил о сложении полномочий через 1 мс после stepDown, m1 о победе на выборах — через 26 мс.
   Без потокового режима изменение обнаружилось бы на очередном опросе (`heartbeatFrequencyMS`,
   10 с по умолчанию) или по ошибке операции.
3. **Выборы проводят узлы, а не драйвер.** `replSetStepDown` ждёт, пока secondary догонит oplog
   (`secondaryCatchUpPeriodSecs`), снимает с узла роль primary и сразу передаёт выборы
   подходящему secondary (election handoff), не дожидаясь таймаута выборов. Новый primary
   сообщает о себе в hello с новым `electionId`; драйвер принимает его и не вернётся к старому, у
   которого `electionId` меньше.
4. **Выбор сервера для каждой операции.** Операция с `readPreference=primary` берёт сервер из
   текущего описания топологии. Пока primary в описании нет, она ждёт его появления (до
   `serverSelectionTimeoutMS=10000`), а не падает сразу.
5. **Если операция всё же попадёт на старый primary**, сервер ответит `NotWritablePrimary`;
   драйвер пометит узел Unknown, запросит немедленную проверку и благодаря `retryWrites=true`
   (retryable reads включены по умолчанию) один раз повторит операцию на новом primary. В этом
   запуске до этого не дошло; повтор на уровне сценария (до 60 попыток) тоже не понадобился.

### Почему majority-подтверждение не гарантирует актуальное чтение с любой secondary

- `w: "majority"` подтверждается, когда изменение сохранено на **большинстве** узлов, здесь — на
  2 из 3. О третьем узле подтверждение ничего не говорит: он может отставать и ещё не получить
  запись.
- Даже узел из этого большинства мог её ещё не **применить**. С MongoDB 8.0 majority-запись
  подтверждается, когда большинство узлов *записало* операцию в свой oplog, а применение oplog к
  данным secondary выполняет отдельный поток асинхронно. В release notes 8.0 сказано прямо:
  чтение с secondary сразу после подтверждения `{w: "majority"}` вне causally consistent сессии
  может не увидеть эту запись.
- `readConcern: "majority"` на secondary тоже не гарантирует свежести: он отдаёт снимок по точке
  majority-commit, известной этому узлу, а узел узнаёт о ней с задержкой.

Majority — гарантия **долговечности**: подтверждённая запись не откатится при смене primary (в
опыте её прочитал уже новый primary). Это не гарантия **видимости** на любом узле. Чтобы читать
свои записи, нужно читать с primary (как здесь, `readPreference=primary`) или использовать
causally consistent сессию с `readConcern: "majority"` и `writeConcern: "majority"`: тогда
чтение несёт `afterClusterTime`, и secondary ждёт, пока догонит эту точку.

## Раздел 7. Шардирование

Коллекция `orders` распределена по `{userId: 1}`: `userId < 2000` — шард A, `[2000, 5000)` —
шард B, `≥ 5000` — шард A.

**1. Какие шарды опросит `mongos`.**

- **История `{userId: 2500}` — только шард B.** В фильтре есть ключ шардирования с условием
  равенства. `mongos` по таблице маршрутизации (метаданные config-серверов, которые он кеширует)
  находит единственный диапазон, содержащий 2500, — `[2000, 5000)` на шарде B — и отправляет
  запрос только туда (targeted query). Фильтр по статусу, сортировку и limit выполняет B.
  Документы с `userId = 2500` по этой карте могут лежать только на B, поэтому опрашивать A
  незачем.
- **Отчёт по `{status: "paid"}` — шарды A и B.** Ключа шардирования в фильтре нет, и ни один
  диапазон исключить нельзя: оплаченные заказы могут быть у любого покупателя, а документы есть
  на обоих шардах. `mongos` рассылает запрос всем шардам коллекции (scatter-gather): каждый
  обрабатывает свои документы (`$match`, `$unwind`, частичная группировка), а итоговые
  группировка, сортировка и limit выполняются при слиянии результатов.

**2. Индекс `{status: 1}` внутри шардов.**

- **Число участников не изменится — по-прежнему A и B.** Маршрутизацию определяют только ключ
  шардирования и карта диапазонов на config-серверах; вторичные индексы шардов `mongos` не
  учитывает. Условие на `status` не говорит, на каком шарде лежат подходящие документы.
- **Индекс меняет работу внутри каждого шарда:** вместо полного просмотра коллекции (COLLSCAN)
  шард найдёт заказы `paid` через IXSCAN по `status` и прочитает только их — меньше прочитанных
  документов, ввода-вывода и процессорного времени. Число опрошенных шардов, сетевые обмены и
  слияние на `mongos` он не меняет. Для отчёта с периодом ещё полезнее `{status: 1, createdAt: 1}`:
  равенство, затем диапазон дат.

## Раздел 8. Результаты и воспроизведение

### Команды

```
docker compose up -d
docker compose run --rm py reset
docker compose run --rm py all            # или по одному: data, index, purchase, failover
docker compose down
```

Каждый сценарий сам готовит данные: `data` — 6 товаров и 35 заказов, `index` — 10 000 заказов,
`purchase` — каталог без заказов, `failover` пересоздаёт базу `hw2_failover`. Запускать их можно
в любом порядке, но не одновременно. `docker compose run --rm lab shell` открывает `mongosh` для
ручных запросов.

### `results/results.json`

Сохранённые результаты получены командами `py reset` и `py all` 21.10.2026 (MongoDB 8.0.30,
PyMongo 4.18.3): все пять сценариев `passed`, `solutionHash` — SHA-256 текущего `solution.py`.
Формат — canonical Extended JSON: Decimal128, int32/int64 и даты сохраняют BSON-типы и точность.
У каждого сценария записаны `status`, `startedAt`/`finishedAt`, версии сервера и драйвера и
список пройденных проверок.

| `reset` | состав загруженного набора |
